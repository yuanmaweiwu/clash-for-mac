> 不评价 UI 审美（见 `docs/UI-AUDIT.md`）；不重复已知限制（无签名、单价内核、多内核待评估）

## 总体判断：最该修的三件事

1. **启动 / 导入 / 切订阅时主线程在解析 YAML 和跑 shell 命令**。`RuntimeConfigBuilder`（Yams load+dump）、`TunGeodataProbe`（整份 YAML 读入 + uppercased）、`SystemNetworkProbe`（3 个同步 `Process`）都在 `@MainActor` 路径上；真实订阅 1–5 MB，用户点「连接」「更新」「开 TUN」时面板会僵几百毫秒，这正是「卡一下」类反馈的来源。
2. **编排逻辑全塞在 `PanelPreviewModel`（1007 行 / 15 条无主 Task），并由此长出状态机缺口**：连接页轮询在内核重启后永久停摆、TUN 与内核启动赛跑、系统代理开关在 `isTransitioning` 时静默返回当作成功。这三条都是「状态与真实任务脱节」，拆成 3 个可测协作者后会被结构挡住。
3. **没有测试底座，静默失败点偏多**。`docs/01-ARCHITECTURE.md` §9 要求的单测一个都没有（只有需 root/联网的 shell harness）；`try?`/空 `catch`/静默 `return` 集中在清理与还原路径上，出问题时只能靠用户复现。先补 4 个纯函数测试 + 2 条不变式断言，再谈其它。

## 不建议改（下轮别动）

1. **订阅磁贴的 3pt 配额条 + 数字并列**：数据可视化例外（§8.5），条只做辅助判断，数字始终同时给出；不要为了「纯装饰」去掉。
2. **二级页用 `PanelRoute` enum + 同宽固定高，不用 `NavigationStack`**：`NSPanel` 场景 + 340pt 固定面板，导航栈会带来尺寸与返回手势的额外状态。
3. **`KernelService.runPipelineWithDeadline` 用 50ms 轮询 + 独立 Task，而非 `withThrowingTaskGroup` 超时**：超时后必须 `task.cancel()` + `provisioner.cancelInFlight()` 才能把下载一起停掉，轮询写法是有意的（注释里已写明）。
4. **`SystemProxyService.forEachServiceConcurrently` 用 `DispatchGroup` + `FailureBox`**：退出路径在主线程，`concurrentPerform` 会把一份 `waitUntilExit` 留在主线程；实测 4 服务并发才进得了 3s 预算。
5. **`AppTerminationGuard` 的 `DispatchSourceSignal` + `MainActor.assumeIsolated`**：注释记录了 `signal()` handler 里跑 `networksetup` 与闭包继承 `@MainActor` 两种实测崩溃；这套写法不要再「简化」。
6. **延迟提示类 `try? await Task.sleep`**（「刚刚更新」「已暂停」等）：被取消即放弃是期望语义；只在 P2 第一条里统一结构，不要改成会往上抛错的版本。
